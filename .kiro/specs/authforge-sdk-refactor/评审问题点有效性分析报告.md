## 逐项分析

### 问题 1：PKCE / OIDC nonce 在 authorize 直发路径被静默丢弃 —— 有效（Critical 成立，但评审表述需修正）

**代码事实**（`libs/drogon/src/controllers/AuthorizationEndpointController.cc`）：
- `authorize()` L93-L98 只提取 `response_type/client_id/redirect_uri/scope/state` 五个参数，**完全不读取** `code_challenge/code_challenge_method/nonce`；
- L365-L372：当 session 已登录且 `evaluateScopes` 全部通过（已有 consent 记录）时，直接以三个空串调用 `generateAuthorizationCode` 并 302 返回授权码。

**评审表述需要修正的部分**：评审称"PKCE 和 OIDC nonce 仍然不可用"，这是**过度概括**。实际上：
- `SessionController::login`（L401-L403/L416-L418 提取，L579-L586 透传）与 `consent`（L720-L722 提取，L814-L821/L854-L861 透传）两条签发路径**均正确透传** PKCE 三元组；
- login 路径还有 `require_pkce_for_public` 配置驱动的强制（L551-L568）；
- token 端点确实校验 `code_verifier`（`TokenEndpointController.cc` L611/L623 提取，`TokenService.cc` L206-L219 校验，S256 委托 `oauth2::pkce::verifyCodeVerifier`）。

**为什么仍然是 Critical**：
1. `TokenService::exchangeCodeForToken` 的 PKCE 校验是**条件式**的——仅当存储的 `codeChallenge` 非空才校验（L206）。authorize 直发路径产生的码 challenge 恒为空 ⇒ **整条 PKCE 防线被绕过**，即使客户端在授权请求 URL 里带了 `code_challenge` 也被静默丢弃。RFC 7636 §4.4 要求授权服务器必须将 `code_challenge` 与授权码关联；静默丢弃比"不支持"更糟——客户端以为自己受 PKCE 保护，实际没有。授权码拦截攻击（RFC 7636 §1 描述的场景）在该路径完全成立，且 PUBLIC 客户端换码无需 client_secret，拦截即可兑换。
2. 触发路径不是边缘场景：**已登录 + 此前已同意**的用户重放 `/oauth2/authorize` 即命中——这正是 returning-user SSO 的最常见路径。首次授权走 login/consent（受保护），之后每次静默授权都不受保护，保护是"一次性"的。
3. nonce 丢弃的独立后果：该路径签发的码兑换出的 `id_token` 无 `nonce` claim（`TokenService.cc` L289-L292 仅在非空时写入）。OIDC Core §3.1.3.7 要求 RP 发送了 nonce 就必须校验一致——严格 RP 会**直接拒绝**该 id_token，这同时是功能性缺陷；宽松 RP 则失去防重放保护。
4. `require_pkce_for_public` 强制只存在于 login 路径，authorize 路径无对应强制，两条路径策略不一致。

**旁证**：`PRD/mfa_auth_code_pkce_design.md` §6.1 已明确记录 SPA 登录现状与 PKCE 改造计划，说明团队已知这一带的债务，但 authorize 直发路径的丢弃行为不在该文档覆盖范围内。

**附带发现**（评审未提）：`MfaController.cc` L601-L608 也传空 challenge，但该码在 L629-L634 由服务端自身立即消费、不经客户端往返，PKCE 在此无意义——**不算问题**，建议加注释说明以免未来误判。

**修复方向**：`authorize()` 提取并透传 `code_challenge/code_challenge_method/nonce` 三参数（与 login/consent 对齐）；同时把 `require_pkce_for_public` 强制逻辑对齐到该路径。改动面小、无兼容性风险（原本带这些参数的请求现状是被静默忽略）。

### 问题 2：client_credentials 不校验 allowedScopes —— 有效（Critical 成立）

**代码事实**（`TokenEndpointController.cc` L767-L769）：
```cpp
// Determine scope (intersection of requested and allowed)   ← 注释是愿望
std::string requestedScope = req->getParameter("scope");
std::string grantedScope = requestedScope.empty() ? "read" : requestedScope;  ← 实现是照单全收
```
注释与实现不符。而且 L740-L744 已经取回了完整的 `OAuth2Client` 对象（`Dto.h` L59 有 `allowedScopes` 字段，DB 层有 `oauth2_client_scopes` 表，V006 迁移），**数据就在手边却没用**。

**规范依据**：RFC 6749 §3.3——请求的 scope 超出客户端许可时，服务器 MUST 以 `invalid_scope` 拒绝或按许可缩窄后签发（缩窄时响应必须带实际 `scope`）。现行为二者都不做。

**应用场景影响**：任意一个合法注册的 CONFIDENTIAL 客户端（只要有 client_secret）可直接请求 `admin` 等特权 scope 并成功拿到 token。项目中受 scope 门控的资源即刻暴露。**部分缓解**：M2M token 的 `userId = "client:<id>"`（L781），若下游同时做 RBAC 角色校验，该主体无角色映射，纯 role 门控的端点不受影响——但这属于纵深防御兜底，不改变 scope 门控被击穿的事实。

**对照**：authorization_code 流程在 authorize 时经 `AuthorizationService::evaluateScopes` 做三层校验（`AuthorizationEndpointController.cc` L304-L338），refresh 只继承存储的 scope（`TokenService.cc` L380）——唯独 client_credentials 是裸的。另外默认值 `"read"` 也值得商榷：RFC 6749 §3.3 允许省略 scope 时用预注册默认值，更正确的默认是该客户端的 `allowedScopes` 全集或显式注册的默认 scope，而非硬编码 `"read"`。

**修复方向**：用 `client->allowedScopes` 与请求 scope 求交集；交集为空或请求超集时返回 `invalid_scope`；省略 scope 时授予客户端注册的默认。修复点单一（一个分支内），风险低。

### 问题 3：Device Code 状态检查与删除非原子 —— 有效，建议 Critical → High

**代码事实**（`TokenEndpointController.cc` L852-L1021）：
- 流程：`findBy`（L852，读）→ client_id 比对（L886）→ 过期检查（L908）→ 状态检查（L926/943/960）→ 生成令牌（L977-L997）→ `saveTokenPair`（L1001）→ 成功回调里才 `deleteBy`（L1009-L1014）；
- `deleteBy` 条件仅 `device_code_hash` 相等，**非** `UPDATE ... WHERE status='approved'` 式原子占用；
- 删除行数被完全忽略：成功回调是空 lambda `[](const size_t) {}`（L1015），失败仅 LOG_WARN。

竞态真实存在：两个并发请求都能读到 `approved`、各自签发一套 access+refresh token，第二个 `deleteBy` 删 0 行也无人察觉。RFC 8628 中 device_code 语义等同授权码，RFC 6749 §4.1.2 对授权码的单次使用要求（重放必须拒绝并撤销已发令牌）按理适用。

**为什么建议降级到 High 而非 Critical**：利用该竞态的前提是**持有 device_code**——它是客户端持有的秘密，正常场景下只有合法轮询方；攻击者需先窃取 device_code 才能与合法客户端并发兑换（窃取后单独兑换本来也成功，竞态只是让"双方都成功且无痕"）。对比问题 2（任意合法客户端未授权提权）攻击门槛明显更高。它更接近"正确性缺陷 + 被盗后无法检测重放"，与授权码重放检测（refresh token family 已有 reuse detection，见 `TokenService.cc` L340-L352）的防护水准不一致。

**修复方向**：将"检查-删除"合并为原子操作——先 `deleteBy(device_code_hash AND status='approved')` 并检查删除行数（=1 才继续签发；=0 返回 `invalid_grant`），或改成 `UPDATE ... SET status='consumed' WHERE ... AND status='approved'` 带行数检查。注意删除时机前移后，`saveTokenPair` 失败会烧掉 device code（用户需重新授权）——这是可接受的安全侧偏差（fail-closed）。

### 问题 4：userInfo 中 `[this]` 捕获 —— 无效（评审误判）

**代码事实**：
- `TokenEndpointController` 继承 `::drogon::HttpController<TokenEndpointController, false>`（头文件 L23）——Drogon 框架管理的**进程级单例控制器**，与应用同生命周期，不会在请求进行中析构；
- L1114 回调中 this 仅用于 `resolvePlugin()`（读取成员 `plugin_`，而 `OAuth2Plugin` 同样是框架管理的全程单例）；
- 同类 `[this]` 捕获遍布全项目（WebAuthnController、MfaController、GitHubController、SessionController、AuthorizationFilter 等数十处），且 `AuthorizationFilter` L92 附近有注释明确论证该捕获的安全性——这是项目既定且论证过的模式。

**判定**：评审以"未继承 enable_shared_from_this ⇒ use-after-free"推断，但 UAF 前提是对象可能在回调执行前析构。Drogon 单例控制器只在进程退出时析构，此时事件循环已停——理论上的 shutdown 竞态属于框架级普遍接受的风险，不是本项目缺陷。若按评审建议改造，需给所有控制器引入 shared_ptr 生命周期管理，与 Drogon 框架的所有权模型冲突，**改造本身才是风险**。

**处置建议**：不修。可选微改进：在 userInfo 的 `[this]` 处加一行注释引用 AuthorizationFilter 的论证，防止后续评审重复报告。

### 问题 5：device_code 兑换不做客户端认证 —— 部分有效（High 保留但需限定范围）

**代码事实**：
- token 端点 device_code 分支（L807-L1060）不调用 `validateClient`，仅要求 `client_id` 参数非空并与 device code 记录中存储值做字符串比对（L886-L901）；
- 签发端 `DeviceAuthController.cc` L156 有 `validateClient(clientId, "", ...)`（空密钥校验存在性）；
- 客户端模型有 `client_type`（CONFIDENTIAL/PUBLIC，V002 迁移 L7），但**无** `token_endpoint_auth_method` 字段。

**规范依据**（RFC 8628 §3.4）：device access token request 沿用 RFC 6749 §3.2.1——**机密客户端必须认证**；公共客户端只需 `client_id` 标识。因此：
- 对 **PUBLIC 客户端**（设备流的典型使用者：电视、CLI 等无法保密的设备）：现行为（client_id 与 device code 绑定比对）**基本符合规范**。评审"完全不验证客户端凭证"的说法对这类客户端不构成缺陷。
- 对 **CONFIDENTIAL 客户端**走设备流：跳过认证确实违反 RFC 8628 §3.4，攻击者窃取 device_code 后无需 client_secret 即可兑换——本应有的第二道防线缺失。

**判定**：有效但必须限定表述——缺陷是"未按 client_type 区分认证要求"，不是"设备流必须客户端认证"。若项目策略是仅允许 PUBLIC 客户端使用设备流，则应在签发端强制 client_type 检查（现在 CONFIDENTIAL 也能发起设备流）。

**修复方向**（二选一，取决于产品决策）：
1. 兑换时按 `client_type` 分支：CONFIDENTIAL → 走 `validateClient(clientId, clientSecret)`；PUBLIC → 维持现状比对；
2. 或在 `DeviceAuthController` 拒绝 CONFIDENTIAL 客户端发起设备流（缩小攻击面，实现最简单）。

### 问题 6：expires_in 硬编码 3600 —— 有效（High 成立，且实际范围比评审列的更大）

**代码事实核实**（评审列的四处全部属实，且各有不同性质）：

| 位置 | expiresAt（真实过期） | expires_in（告知客户端） | 问题性质 |
|------|----------------------|-------------------------|---------|
| `TokenService.cc` L247/L274（auth_code） | `now + accessTokenTtl_`（配置） | 硬编码 3600 | **两者会不一致** |
| `TokenService.cc` L381/L399（refresh） | `now + accessTokenTtl_`（配置） | 硬编码 3600 | **两者会不一致** |
| `TokenEndpointController.cc` L783/L791（client_credentials） | `now + 3600`（硬编码） | 硬编码 3600 | 一致但绕过配置 |
| `TokenEndpointController.cc` L988/L1026（device_code） | `now + 3600`（硬编码） | 硬编码 3600 | 一致但绕过配置 |

配置链完好存在：四份 config 均有 `tokens.access_token_ttl`，`OAuth2Plugin.cc` L54 读取并于 L159-L161 注入 TokenService 构造——**前两处拿着配置却不用在响应里**。

**评审遗漏的同类问题**（本次核查新发现，应一并处理）：
- `TokenService.cc` L288：id_token 的 `exp` 硬编码 `now + 3600`（OIDC Core §2 要求 exp 是真实过期时刻，应有独立的 id_token TTL 或至少跟随配置）；
- `TokenEndpointController.cc` L996：device 流 refresh token 有效期硬编码 `3600*24*30`，绕过 `refresh_token_ttl_` 配置（2592000 恰好相等，改配置即漂移）。

**影响评估**：RFC 6749 §5.1 中 expires_in 语义是令牌真实剩余寿命，客户端据此安排静默刷新。当运维把 `access_token_ttl` 调小（如 600s），前两处路径的客户端会在令牌已死后 50 分钟内持续拿着失效令牌请求（收到 401 才被动刷新）；调大则客户端提前刷新，浪费但不出错。**非安全漏洞，是正确性缺陷**，High 级别恰当（配置一改就出错，且排查方向具有迷惑性）。

**修复方向**：TokenService 两处改用 `accessTokenTtl_`；两个控制器内联路径把 TTL 从 plugin 配置取值（`accessTokenTtl_`/`refreshTokenTtl_` 已是 plugin 成员）；id_token exp 跟随 access token TTL 或引入独立配置。

### 问题 8：validateAccessToken 缺 shared_from_this —— 无效（评审误报）

**代码事实**（`TokenService.cc` L408-L437）：
- 成员 `tokens_`/`crypto_` 只在**同步阶段**使用（L413 判空、L419 hashToken、L420 发起调用）；
- 异步回调 L421-L435 捕获列表仅 `[callback]`，回调体只用参数 `t` 与自由函数 `nowSeconds()`——**不触碰 this 或任何成员**。

**判定**：`shared_from_this` 的作用是保证异步回调执行时对象仍存活。回调不引用对象时，捕获 self 是纯冗余。评审以"与 exchangeCodeForToken 不一致"推断疏漏，但 exchangeCodeForToken（L176）捕获 self 是因为其嵌套续体**确实引用** `grants_/tokens_/crypto_` 等成员（L189、L260 等）——差异是**必要性差异**，不是风格疏漏。此外 TokenService 由 OAuth2Plugin 以 shared_ptr 成员持有（`OAuth2Plugin.h` L399），插件为全程单例，对象实际生命周期覆盖所有在飞请求，双重保险。

**处置建议**：不修。可选微改进：在 validateAccessToken 加一行注释说明"回调不引用 this，故意不捕获 self"，防止未来有人往回调里加成员访问时踩坑——这才是该处真正的（潜在）维护风险。

### 问题 9：JWKS 空响应无 Cache-Control —— 基本无效（且评审的修复方向本身有害）

**代码事实**（`DiscoveryController.cc` L224-L245 + `OAuth2Plugin.cc` L72-L85）：
- 空分支触发条件是 `!plugin || !plugin->getJwkManager()`；
- 而 `jwkManager_` 在 `initAndStart` 中**无条件**构造并 init（无 oidc 配置时也生成临时密钥后发布）——即只要插件加载了，`getJwkManager()` 永不为空。空分支仅在插件本身未加载时可达，而插件未加载时整个 OAuth2 服务都不工作，JWKS 缓存头是最不重要的事。

**更关键的方向性问题**：即便该分支可达，给**空 keys 集合**加 `Cache-Control: public, max-age=3600`（对齐正常分支，评审隐含的修复方向）是**有害**的——下游 RP/网关会把"没有任何验签密钥"缓存一小时，服务恢复后 id_token 验签持续失败。空/降级响应的正确做法恰恰是**不缓存**（`no-store`）或直接返回 503。现状"无缓存头"（HTTP 默认启发式缓存对无验证器的 JSON 响应基本不缓存）反而比"补上缓存头"更接近正确。

**判定**：降为 Info。可选微改进（真要动它）：空分支返回 503 + `Cache-Control: no-store`，语义上更诚实地表达"服务未就绪"。

### 问题 10：client_credentials 缺 issuedAt —— 有效但建议降级 Low，且实际范围更大

**代码事实**：
- `Dto.h` L92：`issuedAt = 0` 默认值；client_credentials 分支（L778-L783）未设置，落库为 0；
- **评审未发现的同类缺失**：`TokenService::exchangeCodeForToken`（L242-L247）与 `refreshAccessToken`（L376-L381）**同样未设置**——即主流程 authorization_code/refresh 签发的所有 token 的 iat 都是 0；只有 device_code 分支（L987）和 GitHub 流程正确设置。评审把它归为 client_credentials 特有问题，实际是**多数路径的共性缺失**，修复时应一并处理，否则只修一处反而加剧不一致。

**影响评估（为什么降级 Low）**：
- RFC 7662 §2.2 中 `iat` 是 OPTIONAL；introspection 实现（L376-L379）在 iat=0 时静默省略该字段——**规范合规**，无协议层错误；
- DB 列 `issued_at bigint NOT NULL` 写 0 不违反约束；
- 实际受损点只有：管理端 token 列表按 `issued_at` 排序（TokenManagementService L130）时 0 值 token 排序错乱，以及审计/取证时无法从存储判断签发时刻。属数据质量/可观测性问题，无安全后果。

**修复方向**：五个签发点统一 `issuedAt = now`（TokenService 两处、client_credentials 一处即可补齐；device/GitHub 已正确）。一行级改动，无风险。
